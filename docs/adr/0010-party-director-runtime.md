# ADR 0010: ハブとステージの進行役（PartyDirector）・ホスト移譲の実装

- 状態: 採用（2026-11-20。本人の「全部作っていい」に基づく。細部は仮の判断を含む）
- 関連: ADR 0005（台帳）、0006（通信方式）、0007（チーム進行）、0008（報酬）、0009（ステージ定義）

## 決定

1. **1人用もオンラインも同じ進行役（`PartyDirector`）で動かす。**
   - ルールを決めるのは「権威」（1人用ならその人、オンラインならホスト）。
   - 参加者は、ステージ・チーム進行・報酬を通信で受け取って表示するだけにする。
   - 1人用の特別な分岐を作らないので、ソロで確かめたことがオンラインでもそのまま成り立つ。
2. **ステージの島（`StageWorld`）は `GameWorld` を継ぐ。**
   - ルール・物理・操作は既存のまま使い、1人用の「F で保存」「落ちたら保存地点へ」だけを止める。
   - 台座の F は全員復活、入口の F はステージへ入る。メニューの「戻る」は全員リセットの投票にする。
3. **チェックポイントの記録は、有効になった瞬間の世界まるごと**（`WorldSnapshot`＋人数別補助の状態）。
   - 全員リセットはこれへ戻す。全員復活は記録を使わず、世界を巻き戻さない。
4. **アバターは各自の PC が動かす**（ホストはその位置を受け取る）。
   - 権威がプレイヤーを動かす（復活・リセット・ステージの開始）ときは、その人の PC へ「ここへ」と頼む。
   - 落下はホストが仲間のアバターの高さで判定する。
5. **報酬**
   - ホストが資格（ADR 0008 の真理値表）を決めて、各自へ配る。
   - 各自が自分の進行に入れて、自分の PC に保存し、受け取ったことを返す。
   - 配った回は部屋がある間は残し、再接続した人へ渡す（ADR 0006 の保証範囲）。
6. **ホスト移譲（ENet）**
   - ホストは 1.5 秒ごとに、次の3つを全員へ配る。
     - 進行の状態（ステージ・台帳・世界・チーム・チェックポイントの記録・報酬の回）
     - 鍵のハッシュとプレイヤー ID の対応表
     - 参加者の IP アドレス
   - ホストが落ちたら、全員が同じ情報から「残った中で ID がいちばん小さい人」を新しいホストに選ぶ。話し合いは要らない。
   - 新しいホストは同じポートで部屋を開き直し、最後の状態から続ける。ほかの人はつなぎ直す。
   - 移譲の間は世界を止め、「ホスト選出中…」を出す。つながらなければ失敗と出す。
   - 鍵そのものは配らず、ハッシュだけを配る（他人になりすませないように）。
7. **相棒ボットは作らない**（2026-11-20 に試作したが、本人が「相棒なくていい」と判断して外した）。
8. **Steam 版**
   - `SteamTransport` に差し替え口だけを置く。**未検証**: GodotSteam と App ID が要る。
   - 提出版は ENet の直接接続。

## 仮にした判断（本人の確認待ち）

| 項目 | いまの挙動 | 根拠・理由 |
|---|---|---|
| ハブの入口 | 最初から3つとも開いている | 新エリアの開放の見せ方は未決（引き継ぎ仕様 5.1）。試遊しやすさを優先 |
| ハブの発展の見た目 | 報酬の名前を文字で出すだけ | 具体の演出は未決 |
| 入口に入る操作 | 入口で F を押した人がいると、部屋の全員でステージへ | 誰が決めるかは未決。ホストの独断にはしない |
| 落下 | 島の下限より下で死亡。ハブには死亡はなく、出現地点へ戻すだけ | 死亡の条件は未決 |
| 復活の位置 | 全員復活はチェックポイントの横に並べる。全員リセットは記録した世界＋チェックポイントの位置 | 正確な配置は未決（引き継ぎ仕様 7-2） |
| 記録の数え方 | 付与回数・受け渡し回数・秒数（一時停止・移譲中も数える） | 厳密な定義は未決（7-10） |
| ホスト移譲の新ホストのポート | 前のホストと同じ番号 | 別 PC ではポート開放が要る。Steam 版ではロビーで解消する |
| 2人でホストが落ちたとき | 引き継ぐ相手がいないので失敗と出す | 「成功したふりをしない」 |
| 同じ能力 ×n の上限 | 上限なし（補助を除けば最大 ×4） | 2026-11-20 本人が「上限なし」に決定（ADR 0011 決定 11） |

## 採らなかった案

- **ステージごとに別のシーンファイルを作る**: `StageDef`（コードのデータ）から組み立てる方が、テストで地形とルールを同時に確かめやすい。
- **ホストがすべてのアバターを物理で動かす**: 遅延がそのまま操作の重さになる。協力ゲームでチート対策は要らない。
- **ホスト移譲で全員が状態を突き合わせて決める**: 決め方が複雑になる。最後に配られた状態と「ID がいちばん小さい人」で足りる。
