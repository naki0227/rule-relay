# ADR 0005: 複数プレイヤーの能力トークン台帳

- 状態: 採用（2026-11-20、P1 マルチ化の第1段。ネットワーク・ハブ・死亡観戦は対象外）
- 出典: `docs/handoff/2026-11-20-multiplayer-handoff.md`、Vault Draft PR #44 `02-Projects/rule-items-world-game-proposal.md` 15〜17・27〜30 節

## 決定

1. **既存の `RuleLedger` を拡張し、別の台帳は作らない。** 「トークンは世界に1つ」をネットワーク抜きの単一台帳で保証し、1人用の呼び出しは `player_id` を省略すると `PLAYER_ID` として従来どおり動く。
2. **トークンの所在を次の4項目で表す**（`RuleToken`）:
   - `vessel_id` = 出自（元の器）。一度決まったら変えない。循環譲渡（A→B→C→A）でも持ち主を付け替えない（本人確定）
   - `holder_ids` = ブロック・生き物・範囲への付与先（従来どおり。プレイヤーは holder にしない）
   - `carrier_id` = 器を離れてそのトークンを持っているプレイヤー（仲間から受け取った・F で回収した・拾った）
   - `lender_id` = 直前に付与・譲渡したプレイヤー。単発の自動返還先、単発を起動できるキーの持ち主
   - `dropped`／`drop_position` = 単発成功時に付与者が退出していて現場に落ちた状態
   器には `owner_id`（器を持つプレイヤー）を足した。
3. **元の器の持ち主の手に渡ったときだけ器へ戻す**（`_deliver`）。それ以外は器なしで持つ。1人用の「回収・単発返還で器に戻る」はこの特殊な場合として残る。
4. **効き方**: 器なしで持つ能力は、その人に効くものとして数える（`ability_count`）。**仮の判断**: 受け取った能力の置き場（ホットバー枠か別枠か）は未決なので、UI が決まるまでは「持っていれば効く」。禁止は手元のどこにあっても効き、能力の数より優先する。
5. **プレイヤーへの付与は `give_to_player` に分ける。** `lend` はこれまでどおりプレイヤーを対象にできない（`CANNOT_TARGET_PLAYER`）。範囲付与をプレイヤーへ広げない（本人確定）。
6. **退出は `set_player_present(id, false)` で印を付けるだけ。** 退出者がブロックへ付けた能力は残り、誰でも F で回収できる（本人確定）。退出者の手元の器・受け取っていた能力の扱いは未決なので、何も消さず動かさない。
7. `validate()` の中身を `LedgerValidator` へ、読み取り専用の問い合わせを `PartyQuery` へ出した（gdlint の公開メソッド数 45・ファイル 800 行の上限内に収めるため）。

## 未決のため仮にした挙動（本人の判断待ち）

| 場面 | いまの挙動 | 理由 |
|---|---|---|
| 禁止をプレイヤーへ直接渡す | 拒否（`PROHIBITION_TO_PLAYER`） | 仕様は「能力を渡せる」まで。ブロック経由で回収すれば禁止も持てる |
| 付与者が退出していて単発が失敗 | ブロックに付けたまま（`complete_single_shot` が false）。F で回収はできる | 引き継ぎ仕様 7-6 で未決。複製も消滅もしない方を選んだ |
| 受け取った能力の効き方・表示 | 持っていれば効く。インベントリでは元の器が「貸出中（仲間が持っている）」 | 引き継ぎ仕様 7-7 で未決 |
| ホットバーに置いた装備品を渡す | 渡せる（受け手は装備せずに効く） | 既存の「ホットバーの装備品は付与の元にできる」に合わせた |

## 採らなかった案

- **パーティー用に別の台帳を作り、1人用の `RuleLedger` と並べる**: トークンが2か所に存在しうるので一意性をテストで保証しにくい。
- **プレイヤーを `holder_ids` に入れる**: 範囲付与・単発・繰り返しなどブロック用の分岐がプレイヤーにも効いてしまう。ブロックへの付与と、仲間の手元にあることを分けた。
- **循環後に持ち主を付け替える（再基準化）**: 本人が「自動で付け替えない」と決めた（Vault 提案書 28 節）。
