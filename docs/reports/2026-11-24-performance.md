# 性能の測定と改善（2026-11-24）

## 目的とやり方

- 目的: 審査員がふつうの Windows PC で遊んでも、重い場面でカクつかないようにする。それまで性能は一度も測っていなかった。
- 道具: `tools/perf_bench.gd` と包みの `tools/perf_bench.sh`（使い方は `docs/how-to-test.md` の「性能を測る」）。
  - 描画: ほかの撮影の道具と同じ lavapipe ＋ xvfb の Forward+。`--fixed-fps 60` で、決まったカメラの道筋を N 秒動かす。
    - 前半はプレイヤーの肩越しの視点で 1 周見回し、後半は撮影用のカメラで島の上を 1 周する。
    - 範囲付与の場面だけは、範囲付与のあと跳ねるブロックを見続ける。
  - 1 コマごとに Godot の Performance の値（フレーム時間・process・物理・描画の呼び出し・描いた物体・三角形）を記録し、
    平均・p95・p99・最大を JSON にする。終わりにノードの数・VRAM・メモリ・`PerfCounts`（見えるメッシュの面の数など）も書く。
  - `--headless` を付けると描かずに CPU だけを測る（スクリプト・物理・アニメーション）。
- 測った場面:

  | 場面 | 中身 |
  |---|---|
  | hub | 全部のステージをクリアした広場（住む生き物 57 匹・建物 57 軒・ポータル 57・置物 約 330） |
  | long_expedition | いちばん大きい島（地形のセル 5,855） |
  | w7_summit_6 | 7-6 頂の祭り（セル 3,730・川・風） |
  | w6_peak_bells | W6 でいちばん大きい島 |
  | w4_herd_path | 生き物が 3 匹いる島 |
  | o2_5 | 寄り道のワールドでいちばん大きい島 |
  | coop4 | 4 人の協力（同じプロセスにホストと参加者 3 人。ENet 127.0.0.1）で 7-6 |
  | range_lend | 広場の草原で、ジャンプを「繰り返し」で範囲に渡す（81 マスが動くブロックになって跳ね続ける） |

- 改善の前は、main（`7a50463`）を書き出したコピーに、この測定の道具だけを足して測った。見た目の仕上げ（ADR 0022、
  `claude/design-polish`。main に #95 で入った）だけの版も同じように測った。改善の後は、このブランチ（仕上げを
  取り込んだ後）を画質の低・中・高で測った。どれも 640×360・3 秒（180 コマ）。`--headless` の CPU は 5 秒。

### 数字の読み方（大事）

- **lavapipe は CPU で描くラスタライザなので、フレーム時間の絶対値は実機の GPU と比べられない**。
  この測定では 1 コマ 0.15〜1.2 秒かかったが、これは CPU で描いているからで、実機の速さではない。
  - Godot の「process の時間」にも lavapipe の描画待ちが入るので、描いている測定ではフレーム時間とほぼ同じになる。
  - さらに、測った PC は 4 コアをほかの作業（テスト・撮影）と分け合っていて（負荷 10〜30）、時間の数字は大きく揺れた。
- **比べてよいのは、描画の呼び出し回数・描いた物体と三角形の数・ノードの数・物理の時間・`--headless` の CPU の時間**。
  描画の呼び出しと三角形は、実機でも同じ数だけ GPU とドライバーに渡る（描画の呼び出しは CPU 側の描画スレッドの
  重さ、三角形は GPU の重さの目安）。
- 描画の呼び出し・三角形は、影の 4 分割の分（同じ物を最大 4 回描く）も含む。

## 見つけた重さ（大きい順）

1. **7-6 の川の泡が 1 コマに 約 170 万の三角形**（7-6 の三角形の 9 割以上）。
   - `WaterVisual` の泡（`CPUParticles3D`）の粒が、既定の `SphereMesh`（64×32 分割、1 粒 約 4,000 三角形）だった。
     直径 12 cm の泡が、川の区切りごとに最大 80 粒、さらに影の 4 分割の分も描かれていた。
   - 4 人の協力（同じ 7-6）でも同じ（179 万）。
2. **広場で地形のセルを動くブロックにすると、画面が 0.3〜0.6 秒止まる**。
   - 範囲付与（81 マス）の瞬間に 約 350 ms。次のコマでさらに地形の見た目の作り直しが 約 250 ms。
   - 1 マスだけでも、地形のメッシュ全体（広場は 8,654 セル）を作り直すので 1 回 120 ms（仕上げの版は頂点の陰が
     入って 250 ms）。
   - 原因は 2 つ:
     - 見た目: 地形が島全体で 1 つのメッシュで、1 マス変わるたびに全部を GDScript で作り直していた。
     - 当たり判定: 1 マスごとに行の箱を消して足していた。体が物理の世界にあるので、箱を足し引きするたびに Jolt が
       体の形（広場は 箱 1,335 個）を全部作り直し、1 マス 約 4 ms。行を探すのにも全セルを毎回調べていた。
3. **広場の描画の数が多い**（描画の呼び出し 平均 1,912・最大 3,623、三角形 平均 100 万）。
   - 置物 約 330 個（木・花・草・小石・街灯・建物）が 1 つずつのノードで、面の数（約 1,200）だけ描画の呼び出しが要った。
     街灯 1 本が 3,224 三角形、家 1 軒が 4,452 三角形と細かい。
   - 住む生き物 57 匹（1 匹で面 約 13）は、遠くで豆粒ほどでも描いていた。
   - 地形は 1 つのメッシュなので、カメラの外の部分も影の 4 分割の分も毎回全部描いていた。
4. **協力の世界の様子（WorldFrame）が大きい**。範囲で 80 マスを動くブロックにすると、1 回 約 4 KB（辞書のまま）。
   1 秒 20 回 × 参加者 3 人で 約 1.9 Mbps をホストが上りで送り、1 回が UDP の 1 パケットに収まらず分割されていた
   （分割の 1 つが落ちると、その回は全部捨てられる）。
5. 範囲付与のプレビュー（右クリックを押している間）は、毎コマ全部の地形のセル（広場で 8,654）を調べていた。

- **重くなかったもの**（`--headless` で測った）: 毎コマの GDScript（`_process`・`_physics_process`）は、広場でも
  1 コマ 2〜4 ms（生き物・ポータル・文字の看板を止めても 1 ms ほどしか変わらない）。ブロック・生き物・看板の
  毎コマの処理は、いまの数ではボトルネックではなかった。物理（Jolt）も、地形を変えた瞬間を除けば軽い。
  当たり判定の箱の数（広場 1,335）も、動かなければ問題にならない。光は日の光 1 つだけで、影を落とす光もこれだけ。

## 画質の設定（低・中・高）

- 見た目の仕上げ（`claude/design-polish`、ADR 0022）が先に「せってい → 画質」の低・中・高（はじめは中）と
  `VisualQuality` を入れたので、**同じ設定に描画の重さの項目を足した**（2 つ目の設定は作らない。ADR 0023）。
  - この作業の途中では別の `QualitySettings`（自動・低・中・高）を作っていたが、合わせるときに消した。
  - 保存は ADR 0022 と同じ `user://settings.cfg` の `[display] quality`（0 = 低、1 = 中、2 = 高）。
  - 置き場所は `src/game/visual_quality.gd` の `TABLE` の 1 か所。画面全体は `VisualQuality.apply_all` →
    `apply_render`、日の光は `WorldLook.apply_quality` → `VisualQuality.apply_sun`。
- 段階の中身（描画の重さの項目。見た目の効果の項目は ADR 0022）:

  | 項目 | 低 | 中（はじめ） | 高 |
  |---|---|---|---|
  | 日の光の影の分割 | 正射影 1 枚 | 2 分割 | 4 分割（改善の前と同じ） |
  | 影を描く距離 | 32 m | 50 m | 60 m（改善の前と同じ） |
  | 影の地図 | 2048 | 4096 | 4096 |
  | 影の縁の計算 | 硬い | ソフト（低） | ソフト（低） |
  | アンチエイリアス | なし | FXAA | MSAA 2x |
  | 3D を描く解像度 | 75%（FSR 1 で拡大） | 100% | 100% |
  | メッシュの LOD の細かさ | 4 px | 2 px | 1 px（既定） |

  ADR 0022 の効果の側は、SSAO が高だけ・光のにじみ・舞う花びら・草の揺れが中と高。
- 判断（AI）: 中を既定にしたまま、中で影を 2 分割・50 m にした。内蔵 GPU のノート PC では、影の分割の数だけ影を
  落とす物を描き直すのが重い。通常の肩越しの視点では、2 分割と 4 分割の違いは遠くの影の細かさだけ。
  - 本人の判断が要る点: 中の影の遠くが、改善の前（4 分割）より少し粗くなる。気になれば高を選べる。

## Windows 版のレンダラー

- いまの設定: `rendering/renderer/rendering_method="forward_plus"`。Windows の描画の下回りは Godot 4.6 の既定
  （Vulkan。使えなければ D3D12、それも無理なら OpenGL の互換レンダラーへ自動で落ちる）。
- 推奨（AI の判断）: **Forward+ のままにする**。
  - この作品の見た目は、SSAO・グロー・トーンマップ（Filmic）・霧に頼っている。Mobile レンダラーには SSAO が無く、
    互換レンダラー（Compatibility）は SSAO が無いうえに、同じ環境の設定で色が白っぽく飛ぶ
    （Vault の [[godot-headless-ci-and-testing]] に記録がある。lavapipe で確かめた）。
  - 光は日の光 1 つだけで、Forward+ の重さの元（たくさんの光のクラスタ処理）はほとんど使っていない。
    重かったのは描く物の数と影で、これはレンダラーを変えなくても、上の直しと画質の設定で下げられる。
  - 内蔵 GPU では中（はじめ）・低の画質で軽くできる。
- 自動で落ちる先が互換レンダラーなのは、古い GPU で「起動しない」よりはよいので、そのままにした（見た目は崩れるが遊べる）。
  Windows 11 の実機・Intel の内蔵 GPU では、まだ試していない。

- `tests/integration/test_perf_budget.gd`（`tools/check.sh` のテストの中で走る）。フレーム時間は PC で違うので確かめない。
  ヘッドレスでも毎回同じになる数だけを確かめる（`src/game/perf_counts.gd` の `PerfCounts`）。
  - 広場（全部クリア）: 見えるメッシュの面（描画の呼び出しの上限）< 2,350、ノード < 3,350、メッシュのノード < 800、
    光 1・影を落とす光 1。直す前は面 2,651・ノード 3,407 で、予算を超える。
  - 重いステージ 5 つ: 面 < 400、ノード < 1,000、影を落とす光 1。
  - 置物は MultiMesh にまとまり、数は減っていない。
  - 1 マスを動くブロックにしたとき作り直す区画は 4 つ以下で、全部を作り直したときと頂点の数と色（陰）が同じ。
  - まとめて 81 マスを抜いても、抜いたマスは土台の上面まで空き、外のマスは地形のまま（光線で確かめる）。
  - 範囲付与の円のセルは、全セルを調べたときと同じ。
  - 世界の様子: 81 マスを抜いたあとの全部の回 < 3,500 バイト、何も動いていない回 < 900 バイトで、セルの一覧は入らない。

  画質を変えると島の日の光の影の分割と距離がすぐ変わる。

## まだやっていないこと・残っている重さ

- **Windows 11 の実機・実際の GPU では、まだ測っていない**。この測定は lavapipe（CPU で描く）で、しかも 4 コアを
  ほかの作業と分け合った PC でのもの。実機の fps は、`tools/perf_bench.sh` を Windows で動かすか、
  エディターのモニターで確かめる必要がある（本人の PC で 1 回見てほしい）。
- 広場のポータル 57 基（1 基 面 11・約 11,000 三角形・渦のアニメーション）は、まだ 1 基ずつのノード。開いている・
  閉じている・クリア済みで渦の色を変えるので、MultiMesh にまとめるには色をインスタンスごとの値にする作り直しが要る。
  モデル（`art/scripts/`）の三角形を減らすのも効く（見た目の仕上げの作業と相談）。
- 住む生き物（面 約 13）・街灯（3,224 三角形）・家（4,452 三角形）のモデルは細かい。Godot の自動 LOD は効いているが、
  MultiMesh にした置物は区画ごとにまとめて LOD を選ぶので、1 本ずつのときより粗さの切り替えが大まか。
- 地形を最初に組み立てる時間（広場で 0.5〜0.9 秒。GDScript で角を丸めたメッシュを作る）は変えていない。
  広場へ戻るたびにかかるので、次に減らすならここ（作ったメッシュを進行の状態ごとに覚えておく、など）。
- 4 人の協力で、参加者の画面の CPU は測っていない（測定は 1 つのプロセスに 4 人分を入れたので、別々の PC の値ではない）。
- `--headless` の物理の時間（Performance の値）は、描かないときは意味のある値にならなかった（コマの合計より大きい）。
  CPU は `--headless` のフレーム時間で見た。
